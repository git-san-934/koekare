# ドキュメント品質レビューチェックリスト

`docs/`配下の各永続的ドキュメントをレビューする際のチェック観点をまとめたテンプレート。各ドキュメント作成後、確認・承認を得る前にこのチェックリストで自己点検する。

## 共通観点（全ドキュメント共通）
- [ ] 曖昧な表現（「適切に」「柔軟に」「必要に応じて」等）が、判断基準なしで使われていないか
- [ ] `glossary.md`の用語定義と表記が一致しているか（未作成の段階では暫定表記であることを明記しているか）
- [ ] 他の永続的ドキュメントとの内容に矛盾がないか
- [ ] 「本書では扱わない／別ドキュメントで定義する」という先送り事項がある場合、どのドキュメントに委譲するか明記されているか

## product-requirements.md 用観点
- [ ] **ビジョンの明確さ**: 複数の差別化要素がある場合、どれが核心価値でどれが手段かの序列が明示されているか
- [ ] **ターゲットユーザーの具体性**: ペルソナが解像度高く記述されているか（属性・利用規模・既存ツールでの離脱経験など）。対象外（Non-Goals）も明記されているか
- [ ] **他セクションとの整合**: ターゲットユーザーの記述が、非機能要件（例: 単一/複数ユーザー前提）と矛盾していないか
- [ ] **成功指標の測定可能性**: 各指標に目標値・測定方法が伴っているか。測定方法が非機能要件（例: オフライン前提）と矛盾していないか
- [ ] **機能要件の詳細化レベル**: 実装可能な詳細まで書くのか、`functional-design.md`に委譲するのかが明示されているか
- [ ] **非機能要件の網羅性**: 少なくとも次のカテゴリを検討したか — パフォーマンス／可用性／データ信頼性／セキュリティ・プライバシー／互換性／ユーザビリティ／保守性・拡張性／スコープ（対応言語・対応OS等の未決事項が残っていないか）

## functional-design.md 用観点
- [ ] `product-requirements.md`の各機能要件が、対応する設計項目でカバーされているか（漏れの有無）
- [ ] データモデル（ER図等）に主要エンティティの属性・関連・多重度が明記されているか
- [ ] スコアリングや判定ロジックなど、`product-requirements.md`で「詳細は本書で定義」とされた項目が実際に定義されているか
- [ ] 画面遷移図・ワイヤフレーム・ユースケース図が必要な範囲で揃っているか（CLIの場合はコマンド一覧・入出力仕様で代替されているか）
- [ ] コンポーネント間の責務分担が明確か（後の`repository-structure.md`と対応づけられる粒度か）

## architecture.md 用観点
- [ ] 技術スタックの選定理由が書かれているか（比較検討なしの断定になっていないか）
- [ ] `product-requirements.md`の非機能要件（パフォーマンス目標、対応OS等）が、技術的な実現方法に落とし込まれているか
- [ ] 開発ツール・手法（テスト、CI等）が具体的に指定されているか
- [ ] 技術的制約（依存ライブラリのバージョン、外部サービス制約等）が明記されているか

## repository-structure.md 用観点
- [ ] 実際のディレクトリ構成と齟齬がないか（作成時点のスナップショットであることが分かるか）
- [ ] 新規ファイルをどこに置くべきかの判断基準が示されているか

## development-guidelines.md 用観点
- [ ] 命名規則・スタイリング規約・テスト規約・Git規約のそれぞれに具体例があるか
- [ ] ルールが曖昧でなく、レビュー時に機械的に判定できる粒度か

## glossary.md 用観点
- [ ] 日本語・英語対応表が、コード上の命名（変数名・関数名等）と一致しているか
- [ ] 用語の定義が循環参照（用語Aの説明に用語Bを使い、Bの説明にAを使う等）していないか
